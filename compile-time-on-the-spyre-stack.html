Compile Time on the Spyre Stack

Technical roadmap for reducing compile time. Four levers, with targets and risks. Implementation is left to the owning teams.

First compile of a large-context model takes about one hour at a 32k sequence length. This cost is paid on first deployment of each model at each shape, and again after any stack upgrade. Most of the hour is the per-SDSC dbo-opt invocations; the remainder is dynamo capture and inductor lowering, where the CP-SAT layout solver is the largest single term.

Summary

Path Cost Status
Cold compile, 32k sequence length ~1 hour today
Warm compile, unchanged model and shapes a few seconds (dynamo only) beta/GA
Incremental recompile, one block changed warm cost + that block's kernels beta/GA
Optimized cold compile, parallel dbo-opt + solver hints reduced backend and lowering terms beta/GA
Symbolic-loop compile, one kernel per shape range one cold compile instead of N stack update

Levers

Lever 1 — Warm compile

Target: a repeat compile of an unchanged model at unchanged shapes costs a few seconds.

Compiled kernels are cacheable artifacts, so a repeat compile can skip inductor lowering, bundle emission, and dbo-opt, paying dynamo cost only. Two lookup tiers are involved: a graph-level entry keyed on the FX graph and shapes, which is what produces the few-seconds figure, and per-SDSC entries keyed on the emitted SDSC JSON, which is what Lever 2 builds on. This is distinct from today's config.sdsc_cache, which deduplicates SDSC JSON within a single bundle and does not survive the process.

Risks

A stale hit returns a wrong kernel silently rather than failing, so the key must cover SDSC content, core count (SENCORES), deeptools build identity, and data format, and needs comprehensive test coverage against stale matching. Because build identity is part of the key, any stack upgrade invalidates every entry, so this lever applies to steady-state operation only.

Lever 2 — Incremental recompile

Target: an edit that changes one block recompiles only that block's kernels.

Per-SDSC cache granularity confines invalidation to the kernels an edit actually changes. Replacing layernorm with rmsnorm leaves every attention kernel bit-identical and recompiles only the norm kernels. Small shape changes behave the same way: changing a sequence length re-tiles attention but can leave elementwise and norm kernels unchanged, and changing a hidden dimension does the reverse.

Risks

Granularity is the whole design decision — bundle-level keying is the simpler implementation and almost never hits during iteration. Compiler-side changes invalidate every entry regardless of granularity, so this lever covers model-side change only.

Lever 3 — Optimized cold compile

Target: reduce the cold-compile hour without changing what gets compiled.

Two independent terms. The dbo-opt invocations are independent per SDSC and currently run serially, so distributing them across host cores reduces the backend term by close to the available parallelism. On the frontend, the CP-SAT layout solver (CpSatLayoutSolver, joint core-division and LX placement, default since config.layout_solver flipped from greedy) dominates lowering time; supplying it hints from a prior solve or from analytic heuristics reduces convergence time.

Risks

Parallelism is bounded by dbo-opt peak memory times concurrency and by the longest single SDSC. Solver hints can steer CP-SAT to a worse layout than a full solve, so device time must be measured alongside convergence time rather than assumed unchanged.

Lever 4 — Symbolic-loop compile

Target: one compiled kernel covers a shape range instead of one compile per shape.

Covering k sequence lengths currently requires k static compilations. With symbolic shapes, loop trip counts resolve from a runtime argument instead of being fixed at compile time. This requires inductor higher-order operators (HOP) to preserve loop structure through lowering rather than specializing at a fixed trip count, and symbolic loop counts in deeptools to emit code that reads them at launch.

Part of the interface exists: mark_dynamic symbols already emit !sdscbundle.input_arg<index, granularity=G, max_value=M> parameters and sdsc_execute carries a symbol_ids list, while the spyre-comms static path emits the symbolicDimInfo_ / coreletSplit_ / rowSplit_ group empty pending dynamic shapes in SDSCSpec.

Risks

A kernel compiled for a range cannot make shape-specific tiling, core-division, or LX residency choices, so expect device-time regression against a static kernel at any single shape in the range. Frontend HOP and backend symbolic loops must both land before either delivers value.
